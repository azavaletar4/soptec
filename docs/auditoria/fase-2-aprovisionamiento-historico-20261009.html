+   * OLT real termino con una configuracion diferente de la pedida (ej. un
+   * firmware que redondea/trunca un valor), para probar que la verificacion
+   * posterior lo detecta en vez de asumir exito.

+export function startFakeOltCli(opts: FakeOltCliOptions = {}) {

+  let currentOnuKey: string | null = null;
+  let hung = false;
+
+  function promptFor(m: Mode): string {

+    if (m === 'config') return 'ZXAN(config)#';

+  function buildGlobalState(): string {
+    const lines: string[] = [];

+      lines.push(`${key}    enable       enable      working      1(GPON)`);
+    }
+    return lines.join('\r\n');

+  function buildRunningConfig(filterPos?: string): string {
+    const byOlt = new Map<string, string[]>();

+      const onuType = opts.renderOverride?.onuType ?? entry.onuType;
+      byOlt.get(pos)!.push(`onu ${key.split(':')[1]} type ${onuType} sn ${entry.serial}`);
+    }
+    const blocks: string[] = [];
+    for (const [pos, lines] of byOlt) {
+      blocks.push(`interface gpon-olt_${pos}`, ...lines.map((l) => ` ${l}`), '!');
+    }
+    for (const [key, entry] of entries) {
+      const pos = key.split(':')[0];
+      if (filterPos && pos !== filterPos) continue;

+      const vlan = opts.renderOverride?.vlan ?? entry.vlan;

+      if (vlan != null) blocks.push(` service-port 1 vport 1 user-vlan ${vlan} vlan ${vlan}`);

+        return;
+      }

+        if (!entries.has(currentOnuKey)) entries.set(currentOnuKey, { onuType: '', serial: '', description: '' });
+        mode = 'if-onu';

+        return;

+          socket.write(`\r\nZXAN(config-if)#`);
+          return;

+        socket.write(`\r\n${buildRunningConfig()}\r\n${TEST_PROMPT}`);

+      }
+      m = line.match(/^show running-config interface gpon-olt_(\d+)\/(\d+)\/(\d+)$/);

+      // simulador todavia no modela rompa la secuencia del test.
+      socket.write(`\r\n${promptFor(mode)}`);
+    },

6 Limitaciones y dudas pendientes

Las rutas Hono nuevas no tienen pruebas HTTP de extremo a extremo

El motor (oltProvisioningService.ts) tiene 19 pruebas reales contra un simulador de CLI completo. Las rutas nuevas en routes/olt.ts (persistencia en olt_provisioning_operations/olt_onts vía supabaseAdmin) se revisaron cuidadosamente a mano pero no hay un arnés de pruebas HTTP para Hono en este repo — construir uno (mock de Supabase + servidor Hono real) es un esfuerzo aparte que no entró en esta fase. Las reviso de nuevo si quieres antes de aprobar.

La clave de idempotencia no detecta un cambio de datos a mitad de reintento

Se genera UNA vez por apertura del modal y no cambia aunque el técnico edite el formulario tras un error (ej. corrige el tipo de ONU). El backend siempre usa los datos del body más reciente para la escritura real (correcto), pero la fila de olt_provisioning_operations conserva el serial/posición del intento ORIGINAL en sus columnas — una inconsistencia cosmética en el historial, no funcional. Aceptable para esta fase; se puede refinar después si molesta en la práctica.

NAP y la referencia MikroTik del contrato siguen sin journaling centralizado

Por diseño arquitectónico del proyecto (ver nota en sección 2), esos dos pasos van directo frontend→Supabase, nunca por Hono — así que no pueden escribir en olt_provisioning_operations.steps server-side. Siguen reportándose como submitWarnings en el modal, igual que antes de esta fase; si uno falla, el técnico ve el aviso pero no queda un registro persistente para reconciliar después (a diferencia de OLT, BD y MikroTik, que sí centraliza runProvisioningPipeline).

El escaneo previo puede ser lento con muchas ONTs

provisionOnt() hace un show running-config de TODO el equipo antes de cada alta (para detectar un serial duplicado en cualquier posición) — ~10s con 675 ONTs reales (confirmado en producción, Fase 1). El timeout del frontend (170s, bajo el límite de nginx de 180s) da margen de sobra, pero cada alta individual tarda más que antes (que solo escaneaba el puerto solicitado). Decisión deliberada: la verificación de serial duplicado en TODO el equipo pesó más que la velocidad.
