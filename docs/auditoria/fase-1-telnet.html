SmartRayco · Fase 1 — Confiabilidad del cliente Telnet

Auditoría del cliente Telnet (ZTE C300)

Confirmación de 4 hallazgos de la auditoría original sobre server/src/telnet/client.ts, más 4 hallazgos adicionales de dos rondas de revisión externa (ChatGPT) sobre las entregas previas — correcciones aplicadas en las 3 rondas, y 21 pruebas automatizadas contra un servidor Telnet simulado (sin tocar el equipo real, sin escrituras). Alcance: solo confiabilidad del transporte Telnet — no se tocó el flujo de aprovisionamiento ni la UI.

Ronda 3 — pendiente de aprobación

1 Hallazgos confirmados

Los 4 puntos de la auditoría se confirmaron leyendo el código real antes de tocar nada.

1. El evento close resolvía éxito aunque faltaran comandos confirmado

socket.on('close', () => { if (!settled) finish(); }) — si la OLT cortaba la conexión a mitad de la secuencia (red, sesión expirada, lo que sea), el cliente igual resolvía la promesa con outputs incompleto, como si todo hubiera salido bien. Cualquier caller (rutas, sync) recibía "éxito" con datos a medio aplicar.

2. Recibir un prompt no confirmaba que el comando fue aceptado confirmado

La única condición para avanzar al siguiente comando era PROMPT_RE.test(buffer) (línea terminada en # o >). La ZXA10 C300 vuelve a mostrar el mismo prompt tanto si el comando fue aceptado como si lo rechazó con un error CLI (%Error 20204, Invalid input detected, Incomplete command — todos ya documentados como reales en los comentarios de zteCommands.ts). No había ninguna detección de esos errores: el cliente seguía mandando el resto de la secuencia como si el comando rechazado hubiera funcionado.

3. Los logs de timeout podían exponer comandos/respuestas sensibles confirmado

El único log con contenido crudo (console.error en el setTimeout del timer) imprimía commands[commandIndex] y accumulated + buffer tal cual. Comandos reales como configureWanPppoeCommands incluyen la clave PPPoE del cliente en texto plano (wan-ip ... username X password Y ...) — un timeout durante ese comando habría impreso la clave completa en los logs del backend.

4. El filtrado IAC no soportaba fragmentación entre paquetes TCP confirmado

stripIac() procesaba cada chunk de forma aislada, sin ningún estado compartido entre llamadas. Un IAC suelto al final de un paquete, un DO/WILL sin su byte de opción todavía, o sobre todo una subnegociación (IAC SB ... IAC SE, que puede ser larga) cortada justo en el límite de un paquete, se interpretaban mal — en el peor caso, bytes de control colados en el texto que después se compara contra PROMPT_RE/MORE_RE.

Ronda 2 — 3 hallazgos adicionales de la revisión externa (ChatGPT), confirmados y corregidos:

5. La redacción de la ronda 1 no cubría una credencial filtrada FUERA de un comando confirmado

redactSensitive() solo enmascaraba texto con la forma literal password <valor>/username <valor> — pero el log de timeout también imprimía el buffer crudo recibido del equipo, que durante el login puede contener texto como Password:\n<lo que sea> sin la palabra "password" pegada al valor en la misma línea. Caso concreto señalado: un timeout ocurriendo justo después de que el equipo mandara Password: seguido de más texto, con ese texto todavía en el buffer — el regex de redacción no lo detectaba y se imprimía tal cual.

6. detectCliError clasificaba estadísticas normales como rechazo confirmado

El regex de la ronda 1 (^%?\s*error\b) hacía match con cualquier línea que empezara con la palabra "Error", sin exigir que fuera realmente un código de rechazo. Caso concreto señalado: una línea de contador tipo Error packets: 0 (común en salidas de show interface/show pon power) se clasificaba como un error CLI real y abortaba la secuencia completa, aunque el comando en realidad se hubiera ejecutado bien.

7. La respuesta a "terminal length 0" nunca se validaba confirmado

El cliente mandaba terminal length 0 y, con solo ver cualquier prompt de vuelta, asumía que había funcionado — sin pasar esa respuesta por ninguna detección de error. Si algún firmware/variante rechazara esa sintaxis puntual, el cliente seguiría en silencio con la paginación aún activa (el mismo bug de fondo de "646/675 vs 675/675" ya documentado en client.ts), sin que nadie se enterara.

Ronda 3 — 1 hallazgo adicional, esta vez en el arnés de pruebas (no en el cliente de producción):

8. fakeOltServer.ts (servidor simulado) era flaky con negociación tardía confirmado

ChatGPT corrió las 20 pruebas con Node 24 y obtuvo 19/20 — el test "negociación IAC fragmentada" falló de forma aislada, con cierre durante login:clave. Causa real: el simulador solo descartaba bytes de negociación antes de escribir "Username:" (bandera acceptInput) — pero las respuestas de negociación del cliente (declina DO/WILL con WONT/DONT) viajan en un flujo de bytes independiente del que escribe el simulador, sin ningún orden garantizado entre ambos. Una respuesta tardía que llegara después de que el simulador ya hubiera escrito "Username:"/"Password:" se colaba cruda en el buffer de línea, rompiendo la comparación de usuario/clave. Esto es un bug del arnés de pruebas, no del cliente real (client.ts) — se confirmó deliberadamente revirtiendo el fix y viendo fallar la nueva prueba determinista (ver sección 5), antes de restaurarlo.

2 Correcciones implementadas

Todas en server/src/telnet/client.ts (rondas 1-2) salvo la nota de alcance del lock y, en esta ronda 3, el fix vive solo en el arnés de pruebas (fakeOltServer.ts) — client.ts no se tocó porque no se identificó ningún fallo suyo, solo del simulador que lo pone a prueba.

  1. Cierre antes de completar = siempre rechazo. socket.on('close', ...) ya no llama finish() — ahora rechaza con un error explícito indicando en qué comando (de cuántos) se cortó. La única forma de resolver éxito sigue siendo terminar la secuencia completa normalmente.
  2. Detección centralizada de errores CLI (detectCliError, exportada): revisa cada línea de la respuesta de un comando contra patrones ya confirmados contra el equipo real (%Error 20204, Invalid input detected, Incomplete command) más variantes estilo Cisco como respaldo (Unrecognized command, Ambiguous command). Solo revisa el inicio de cada línea — el eco del comando enviado queda siempre después del prompt en la misma línea, nunca al principio de una línea nueva, así que un valor de texto libre que contenga la palabra "error" en medio (ej. una descripción de cliente) no dispara un falso positivo.
  3. Detener la secuencia al primer error: si detectCliError encuentra algo, se llama fail() inmediatamente — el socket se destruye ahí mismo y nunca se llega a mandar el siguiente comando de la lista.
  4. Filtro IAC con estado persistente entre paquetes: stripIac ahora es una máquina de estados (data / iac / negotiate / sub / subIac) declarada en el mismo scope que el resto del estado de la conexión, así que sobrevive entre llamadas — una secuencia IAC partida en cualquier punto entre dos o más paquetes TCP se resuelve correctamente apenas llega el resto. Se preservó el mismo comportamiento de siempre (declinar DO/WILL con WONT/DONT, ignorar el contenido de las subnegociaciones) y se corrigió además un caso no cubierto antes: IAC IAC (byte de datos 0xFF escapado) ya no se interpretaba bien.
  5. Ronda 2 — logs de timeout/error con metadatos, nunca contenido crudo: en vez de intentar enmascarar el comando/buffer con un regex (redactSensitive, que la ronda 1 aplicaba ahí y que no cubría el caso de una credencial filtrada por el propio equipo durante el login, fuera de la forma password <valor>), el log de timeout y el error de cierre prematuro ya no imprimen ningún comando ni buffer — solo 4 metadatos seguros: fase (login:usuario / login:clave / post-login:terminal-length / comandos), comando (índice/total), duracionMs (desde que se empezó a esperar esa respuesta) y bytesPendientes (tamaño del buffer sin contenido). Esto elimina la clase entera de bug, no solo el caso puntual reportado. redactSensitive se conserva solo como defensa adicional sobre la línea de error que devuelve el equipo (no sobre comandos propios) y commandVerb() (nuevo) identifica el comando rechazado por su primer token (ej. wan-ip) — nunca puede ser una credencial, así que es seguro mostrarlo sin redacción.
  6. Ronda 2 — CLI_ERROR_LINE_RE acotado a rechazos reales: ya no basta con que una línea empiece con la palabra "Error" — ahora se exige un código numérico pegado (Error 20202:), que es el formato real confirmado contra el equipo. Las variantes "Unrecognized command"/"Ambiguous command" (nunca confirmadas en este equipo, puro respaldo estilo Cisco) ahora exigen el % inicial típico de esa convención, para no ampliar de más la superficie de falsos positivos con algo ya especulativo de por sí. Una línea de estadísticas como Error packets: 0 ya no dispara nada.
  7. Ronda 2 — respuesta a "terminal length 0" verificada explícitamente: ahora pasa por detectCliError igual que cualquier otro comando. Si el equipo la rechaza, no se aborta la conexión (la paginación "--More--" ya es genérica para cualquier comando, así que la sesión sigue siendo funcional, solo sin el atajo de desactivarla) — se deja constancia explícita en un log (sin contenido sensible posible, esa respuesta nunca trae una credencial) en vez de ignorarlo en silencio como antes.
  8. Ronda 3 — filtro IAC persistente en fakeOltServer.ts durante TODA la conexión (no en client.ts, ver hallazgo 8): se reemplazó la bandera acceptInput (que solo descartaba bytes antes de "Username:") por una máquina de estados IAC (data/iac/opt/sub/subIac) que corre sobre cada chunk entrante durante toda la vida de la conexión, con estado persistente entre chunks — el mismo patrón que ya usa stripIac() en el cliente real. Así, una respuesta de negociación del cliente que llegue en cualquier momento (incluso pegada en el mismo paquete que el usuario o la clave) se separa del texto real antes de buscar líneas, sin depender de que llegue antes o después de ningún prompt.
  9. Paginación y prompts de la C300: sin cambios de comportamiento — se conserva MORE_RE/MORE_CLEAN_RE y la heurística de prompt ya validada.
  10. Serialización de sesiones por OLT (oltTelnetLock.ts): sin cambios de código — se agregó un comentario documentando que el candado es un Map en memoria de un solo proceso Node, no distribuido. Hoy es seguro porque ambos ecosystem*.config.cjs corren un único proceso backend sin modo cluster; si eso cambiara, el candado dejaría de alcanzar y haría falta coordinarlo afuera del proceso.
  11. Propagación de errores en rutas y sync: revisado — routes/olt.ts, oltSyncService.ts y debtHoldService.ts ya envuelven cada runTelnetCommands en try/catch y propagan el error (502 al frontend, o console.error + conteo de failedPorts en el sync). El problema real nunca estuvo en cómo propagan el error estos callers, sino en que el cliente Telnet no rechazaba cuando debía — con las correcciones de arriba, esas rutas ahora reciben el rechazo correcto sin necesitar cambios propios.

+/** Espera hasta que el texto acumulado recibido por `socket` contenga `needle`
+ * (busqueda simple, sin preocuparse por bytes de control: alcanza para
+ * ubicar los prompts de texto plano "Username:"/"Password:"/el prompt). */
+function waitForText(socket: Socket, needle: string, timeoutMs = 2000): Promise<void> {
+  return new Promise((resolve, reject) => {
+    let buf = '';
+    const timer = setTimeout(() => {
+      socket.off('data', onData);
+      reject(new Error(`timeout esperando "${needle}" (recibido hasta ahora: ${JSON.stringify(buf)})`));
+    }, timeoutMs);
+    function onData(chunk: Buffer) {
+      buf += chunk.toString('latin1');
+      if (buf.includes(needle)) {
+        clearTimeout(timer);
+        socket.off('data', onData);
+        resolve();
+      }
+    }
+    socket.on('data', onData);
+  });
+}
